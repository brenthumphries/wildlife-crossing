## Also this session: review authority and the merge gate

### What got done

- **ADR 0020 written and accepted.** PR #10 merged as `a8bc28c`. Three commits:
  `8dac498` the ADR, `f4af35b` marking ADR 0019 superseded in part,
  `6c6891c` pointing `pipeline-design` §7.1 and `CONTRIBUTING.md` at it. It was
  drafted `proposed`, the first of the twenty not accepted on arrival, and
  accepted the same day once D1 and D2 were ruled on.
- **[ADR 0019](../../docs/adr/0019-dco-sign-off-on-automated-commits.md) is
  `superseded-by-0020`.** Its Context and reasoning are untouched, because they
  are why ADR 0020 took the migration path ADR 0019 had already named for
  itself.
- **Everything in the Next session block above has landed.** PR #9 `37bd3a5`
  (the vault three), PR #10 `a8bc28c` (ADR 0020 and its pointers). Ten pull
  requests merged in project history now, three of them today.

### What the analysis found

- **Auto-merge answers when, never who.** It cannot bypass ruleset `22403399`,
  it waits for all five contexts, and the enabling click is the product
  owner's. It does not contradict ADR 0019's claim that "nothing signed in
  advance enters the project without the product owner's merge", which says the
  product owner's merge rather than a click at the moment CI turns green. The
  concern raised against it on 09-08 was looser than the ADR is.
- **The real gap is that there is no review gate at all.**
  `required_approving_review_count: 0`, `require_code_owner_review: false`,
  `require_last_push_approval: false`, and no `CODEOWNERS` file. The rule that
  the product owner decides what merges is currently enforced by there being
  exactly one writer, which is a property of the membership rather than of the
  configuration.
- **ADR 0019 blocked the obvious fix.** GitHub does not let an author approve
  their own pull request, and ADR 0019 made every automated commit the product
  owner's, so a required review could never gate automated work.
- **ADR 0019's own escape hatch does not fit the current ruleset.** It puts the
  trailer in the squash-merge message; `allowed_merge_methods` is `["merge"]`
  only. ADR 0020 D2 uses the merge commit body instead.
- **`require_last_push_approval` is the precise hole**, sharper than
  `dismiss_stale_reviews_on_push`: it is what stops an approval being followed
  by a push that auto-merge then lands.

### Decisions made

- **D1 and D2 approved by Brent.** The pipeline gets its own machine account,
  and ADR 0019's attestation moves to merge time. D3, that self-authored pull
  requests are gated by checks alone, was written as a description of a residue
  rather than a choice and was not separately ruled on.
- **A second personal login for reviewing was considered and rejected.**
  GitHub's terms allow one free account per person plus a machine account that
  "can only be used for running a machine", so it is not available. The
  deciding objection is not the policy: an approval from an account the author
  controls certifies nothing the author's own judgment did not, which is the
  failure ADR 0019 already refused one layer down when it rejected a bot
  signing the DCO as itself.
- **Two doc-pointer edits were added to the ADR pull request unasked**, on the
  argument that landing a supersession while two documents still assert the
  superseded rule manufactures a §4 drift row. Accepted.

### Open questions / blockers

- **The machine account does not exist.** D1 and D2 are accepted and

- **The ruleset changes are keyed to an event, not a date.** `CODEOWNERS`,

  repository.** The *Tool tests* context went red on PR #12 and the merge was
  blocked until it was fixed. Ruleset `22403399` had admitted eleven pull
  requests and refused none.

### What the analysis found

- **The recurring `.git/index.lock` is largely explained, and the proven half is
  narrow.** A session working through the mounted folder can create and rename
  but cannot unlink. Git takes a lock, does its work, and fails to remove it.
  `git reset` from such a session prints `unable to unlink` for `HEAD.lock`,
  `refs/heads/main.lock` and `index.lock` together. That accounts for the locks
  always being zero bytes, for no git process ever running when one is found,
  and for the unmoved mtime [[../build-reviews/2026-08-25-next-build]] measured
  when it disproved the harness theory. That theory was wrong and the review was
  right to record the cause as unknown rather than guess again.
- **The evidence had been filed where nobody looked.** `.git/_stale_locks/`
  holds 15 parked `index.lock.<pid>` files dated one per recent session day,
  plus `.git/__probe` from 2026-06-28 and `.git/_stale_lock_2` from 2026-08-11.
  None is a git file. Earlier sessions hit the same wall and moved the lock
  aside. Recorded but not implicated: `lsof` shows a `com.apple` process holding
  read-only descriptors across `.git`, consistent with an indexer, and
  read-only descriptors do not create locks.
- **`ship.py` cannot express a rename.** `staged_paths()` reads
  `git diff --cached --name-only`, which collapses a rename to its destination,
  while a plan names literal paths. Commit 5 of a 5-commit plan therefore failed
  verification after four had already landed. Worked around with
  `diff.renames false` for one run. The commit object is identical either way.
- **A test passed on every machine it was written on and failed on the only one
  that mattered.** It asserted two findings by counting `"::error::"` plus
  `"error:"`. `::error::` contains `error:`, so under GitHub Actions each
  finding counted twice and the assertion read 4 against 2. Locally
  `GITHUB_ACTIONS` is unset, the plain form prints, and the arithmetic came out
  right. Fixed to count the message fragment, verified with the variable set
  and unset.
- **A cloud session can clone this repository unauthenticated and cannot reach
  its API.** `git ls-remote` returns the true head from both the cloud container
  and the linked machine. `api.github.com` answers the cloud session **403**,
  *"GitHub access to this repository is not enabled for this session"*, which is
  an egress policy denial rather than an authentication failure, so a token
  would not change it. `api.github.com/rate_limit` answers 5,000 requests with 0
  used where anonymous GitHub allows 60, so that reply is not GitHub's. The
  daily task's premise that it was fighting stale caches is better explained by
  an interception layer.

  Brent's call.** `open-day` proposes bundles of unblocked, autonomous,
  file-disjoint work in the morning and dispatches what is selected;
  `close-day` runs the evening accept, reject and merge gate and closes the day
  clean. Scheduled tasks call the same skills rather than carrying their own
  prompts. The daily project-state task dissolves into `open-day`.
- **The daily task's job is dispatch, not status. Brent's call.** Anything on
  its page that cannot change which bundle gets picked belongs in the weekly
  review instead. That removes roughly half of it, including the suite figures,
  the pipeline diagram and the settled-decision history.
- **`/morning` stays separate from `open-day`.** It is life-wide and this is
  repository-wide. Reversible.
- **`docs/testing-setup.md` corrected in the same commit that added its
  checker**, so the check landed green rather than red on arrival.
- **The vault leftovers from the previous session were committed first**, as

- **`ship.py`'s rename bug is unfixed.** The fix is `--no-renames` in
