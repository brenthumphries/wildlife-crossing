## What I worked on

Updated all PRDs where map tiles are referenced to assume hexagonal tiles
rather than square tiles — including the downstream design implications, not
just a text substitution.

## What got done

- **[[game-design-overview]]**: updated the Movement and mortality section to
  describe hex 6-directional pathfinding (each tile has exactly 6 direct
  neighbours; no diagonal relationships exist). Updated the `edge_penalty`
  comment in the habitat quality formula to clarify that perimeter is measured
  as exposed hex edges (6 per tile) rather than 4-sided adjacency.
- **[[wildlife-overpass-crossing]]**: updated the resolved open question on
  diagonal pathfinding to explain the hex grid model and why crossing choice
  remains unambiguous.
- **[[crossing-location-selection]]**: clarified the segment-zoom threshold
  resolution — for hex tiles, the ≥16 px size is measured as flat-to-flat
  width (the hex's shorter axis).
- **[[fable-wildlife-crossing]]** and **[[fable-migration-plan]]**: updated all
  mirrored references to 4-directional pathfinding to match the hex
  6-directional model, including the decision log row and the migration map.

## Decisions made

- Map tiles are hexagonal, not square. This was a product-owner decision; PRDs
  updated to reflect it. No ADR written yet — may warrant one once the hex
  coordinate system is chosen for implementation (axial vs. cube coordinates).

## Open questions / blockers

- **Hex coordinate system not yet specified.** The PRDs now consistently
  describe hex 6-directional pathfinding, but the actual coordinate system
  (axial, cube, offset) is an implementation decision not yet documented.
  Should be addressed in the technical architecture doc or a dedicated ADR
  before the pathfinding system is built.
- **Overpass spanning on a hex grid.** The PRDs describe overpasses spanning
  "every cell of dangerous terrain," which is still valid on a hex grid. But
  road/barrier orientation on a hex grid is more varied than on a square grid
  (roads can follow any of 3 hex axis directions). Worth revisiting the
  overpass placement mechanics in [[wildlife-overpass-crossing]] during
  implementation to confirm the spanning model holds.

## Next session

- Consider writing an ADR for the hex coordinate system choice once
  implementation begins.
- Revisit [[wildlife-overpass-crossing]] overpass placement mechanics in light
  of hex road orientation if/when road data is being designed.

  `information_manager`, `permissions_manager`, `time_controller`,
  `milestone_tracker`, `narrative_manager`) — kept as world-subtree systems, not

  the "every requirement → one phase" rule stays exact.

### Resolved (from this morning's open questions)

- **Hex coordinate system** → [0002 hex-grid topology] standardizes on axial
  coordinates internally with cube coordinates for distance math; also documented
  in `architecture.md` §1. (Closes the "not yet specified… address in the
  architecture doc or a dedicated ADR" item.)
- **Overpass spanning on a hex grid** → addressed in `simulation-design.md` §3
  and [0003 crossing tile architecture]: a span is complete iff every dangerous
  cell of the segment is covered by a connected, single-type crossing chain. The
  spanning model holds on hex; edge-based adjacency makes it cleaner, not harder.
