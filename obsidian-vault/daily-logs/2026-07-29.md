## What got done

- **Verified the code already matches the B5 decision.** `game/data/sub_areas.json`
  has `starts_unlocked: true` on sub-area 7 only; all 11 others are `false`.
  `world_select_controller.gd` derives lock state from that field and already
  desaturates + locks everything but Bow Valley, blocking zoom at the boundary.
  `main.gd:33` loads only `TUTORIAL_SUB_AREA` (7). Nothing needed to change to
  *implement* the scope — it was already the de facto behaviour, just never
  written down as a decision.
- **Fixed the one place that read as a bug rather than a decision.**
  `main.gd:127`'s guard message cited a stale internal ref ("B4") and said the
  sub-area "is not loaded yet" — future tense, sounds like unfinished work.
  Reworded to state the scope directly: locked, v0.1.0 is Bow Valley only.
- **Logged the decision in `docs/roadmap.md`** (Phase 2, after the exit
  criteria), matching the existing "Decision logged" convention already used
  in §8. States what's locked, why (Phase 5 unlock system doesn't exist yet),
  and why Bow Valley specifically is safe to ship alone (it's one of only two
  sub-areas whose corridor bisects the map, so the tutorial mechanic can't
  silently fail to demonstrate — see [[../design/detour-cost-question]]).
- **B6 — closed.** Brent unpacked the downloaded macOS `.app`
  (`wildlife-crossing-desktop-builds/wildlife-crossing-macos/`), cleared
  quarantine, and launched it windowed: reaches the Bow Valley tutorial,
  animals visibly moving along the corridor, **B** builds the overpass
  (chime plays), **M** opens the world map with sub-area 7 unlocked and the
  other 11 locked — matching today's B5 decision exactly.
- **Found and fixed a macOS-only bug in `tools/smoke_boot.sh`.** Two rounds:
  1. `timeout` isn't on stock macOS (GNU coreutils only) — the script now
     detects `timeout`/`gtimeout` and fails with an actionable message
     (`brew install coreutils`) instead of a cryptic exit 127 that
     `analyse_log` misreported as "did not reach the tutorial." Same class of
     bug the script exists to prevent.
  2. Once `gtimeout` was installed, the smoke test still reported **0 lines
     of output on a boot we knew was healthy** (already confirmed playable
     in the windowed test). Diagnosed by hand with Brent, ruling out causes
     one at a time: foreground run showed the banner + `Tutorial loaded`
     live (confirms the binary prints fine); backgrounded + `kill` (no
     `gtimeout` involved) still lost it; `kill -INT` instead of the default
     SIGTERM still lost it. Root cause: **macOS silently drops a killed
     process's buffered stdout**, and a healthy boot only logs a handful of
     short lines before going idle — never enough to hit the buffer's flush
     threshold on its own. Confirmed the fix live: wrapping the binary in
     `gstdbuf -oL -eL` (same `coreutils` package) forces line buffering and
     the log came through — 3 lines, `Tutorial loaded`, exit 0. Linux does
     not have this problem (reproduced against the real project in the
     sandbox: a plain `timeout`-killed boot came through with no wrapper
     needed) — wrapped unconditionally on both platforms anyway, so behaviour
     doesn't silently depend on which OS runs it.
  3. Documented both fixes in the script header and in
     [testing-setup.md](../../docs/testing-setup.md) (new "Smoke-testing an
     exported build" section) so this isn't re-derived next time.
- **B3 — closed.** `InfrastructureManager.try_complete()` no longer requires
  every dangerous tile of a segment to be covered; it checks whether the
  player's *placed* tiles contain a connected "core" whose local safe ring
  splits into two or more sides (ADR 0016 rule 3) — implemented as a bounded
  BFS growing connected subsets of the placed set up to `MAX_CORE_TILES = 4`
  (named constant, documented at the definition per the ADR's own
  requirement), testing the ring at each size via a flood-fill component
  count. Hand-verified the algorithm against all seven rows of the ADR's
  worked table before writing any test — e.g. confirmed by hand that
  `{(12,5),(13,5)}`'s ring splits into a west pair and an east pair (valid),
  while `{(12,5)}` alone's ring is one connected piece (invalid) — then wrote
  all seven rows as named cases in `infrastructure_manager_test.gd` and
  confirmed empirically: every hand prediction matched the test run.
  `build_full()` → `build_span(segment_id, crossing_type, tiles)`, taking an
  explicit span location instead of paving the whole corridor (ADR's own
  "renamed and re-scoped" follow-on item). `Simulation.build_crossing()` and
  both `main.gd` call sites (KEY_B, confirm-panel hand-off) now pass a new
  `TUTORIAL_SPAN` constant — the ADR's worked minimal example,
  `{(12,5),(13,5)}` — as an explicit interim default until B4's real
  placement UI exists; pressing **B** now builds a 2-tile, 10,000-cost
  overpass instead of paving all 20 tiles for 100,000, which is the actual
  defect this blocker names. Also fixed a now-stale comment in
  `data_validation_test.gd` that referenced the old whole-segment completion
  rule. Full suite: 15 scripts / **122** tests / 2,750 asserts, all green
  (was 116/2,740 this morning).

## Decisions made

- **B5 resolved: scoped, not built out.** First build ships sub-area 7 only.
  The other 11 sub-areas stay authored and data-complete but locked until
  Phase 5's trust/permissions system exists to unlock them. Rejected building
  the general sub-area load path now — it would let a player reach content
  with no unlock story behind it, and it's strictly more work than the
  roadmap needs for a first playable.
- **The v0.1.0 release note will restate this scope, not just the roadmap.**
  `docs/release-notes/` is still empty (V7 hasn't run — it depends on B6, B3,
  C1). Not writing a release note for a build that hasn't shipped; flagging
  this here so V7 doesn't have to re-derive the reasoning.
- **`smoke_boot.sh` wraps every platform in `stdbuf`/`gstdbuf`, not just
  macOS.** Cheaper than branching on OS, and it means the two platforms are
  no longer relying on an undocumented difference in libc/kernel behaviour
  that could change under us.
- **`MAX_CORE_TILES = 4`, not unbounded.** ADR 0016 requires the cap be a
  documented constant since naive connected-subset enumeration is exponential.
  4 covers every verified case (minimal spans are 1-2 tiles) with margin; raise
  it if a future corridor's minimal span needs more.
- **`TUTORIAL_SPAN` is a real design placeholder, not a hidden shortcut.**
  There's still no way for a player to choose a span location — that's B4,
  explicitly out of scope here. Hardcoding the ADR's own verified minimal span
  keeps the tutorial playable and correct in the meantime rather than
  regressing to "pressing B does nothing" or reintroducing the whole-segment
  bug. Called out in comments at both `main.gd` and this log so it isn't
  mistaken for the finished feature.
